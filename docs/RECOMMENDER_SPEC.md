## 0. Что должна делать система

**Главный сценарий:** я играю на герое **H**. На 10-й минуте я кликнул по вражескому Axe и увидел у него Heart of Tarrasque.
Программа говорит: «Axe собрал Heart of Tarrasque → на Juggernaut: **Eye of Skadi** (режет лечение)».

Запрос: `(мой герой H, враг E, предмет врага X, мои предметы, игровое время, моё золото, режим, мой ранг)`.
Ответ: 1–2 предмета **для героя H**, почему (механика), насколько уверены.

Второстепенный сценарий (начало катки): вражеские предметы ещё не видны, поэтому совет строится против самого героя E.

Совет **всегда персональный под H**. Обобщение до «похожих героев» допускается только при нехватке данных, и тогда это явно помечается.

## 1. Что не так в текущей реализации (не повторять)

1. **Сохраняются только суммы, сырые матчи выбрасываются.** Любое изменение метрики требует пересобирать данные. Это главная причина потерь времени.
2. **Нет контроля длительности и богатства.** Предметы берутся из **итогового** инвентаря. В длинной игре у всех больше дорогих предметов, а у врага чаще будет Heart. Поэтому «против Heart на мне часто Skadi» может значить просто «игра была длинной». Нужно сравнивать внутри одинаковых по длительности и уровню фарма игр (раздел 4).
3. **Сравнение «против X» с «в целом».** Базой должны быть игры, где у врага **нет** X, а не все игры.
4. **Жёсткие пороги вместо сглаживания.** Сейчас при 29 играх результат выбрасывается, а при 30 принимается на веру. Нужно сглаживание (раздел 5).
5. **Апгрейды.** Если Orchid собрали в Bloodthorn, Orchid пропадает из итогового инвентаря. Нужно засчитывать предмет, если он есть сам или есть предмет, в который он собирается.
6. **`vs_item` = «X у любого врага».** Этого мало: нужна ещё связка «X именно у героя E».
7. **Нет рангов.** Решается объединением с OpenDota (раздел 2.3).

## 2. Сбор данных

### 2.1. Хранить сырые матчи
Сборщик (GitHub Actions) пишет **сырые компактные записи** каждого подходящего матча в Parquet, **один файл на день**: `raw/2026-09-29.parquet`. Файлы публикуются как ассеты релиза `data-raw` и дописываются раз в сутки, старые не перезаписываются.

Схема строки (одна строка = один игрок в матче, 10 строк на матч):

| поле | тип | откуда |
|---|---|---|
| match_id | int64 | Steam |
| start_time | int32 | Steam |
| duration | int16 | Steam |
| game_mode | int8 | Steam |
| lobby_type | int8 | Steam |
| radiant_win | bool | Steam |
| patch | str | по дате, из dotaconstants |
| is_radiant | bool | player_slot |
| hero_id | int16 | Steam |
| items | list<int16> | item_0..5 + backpack_0..2 (итоговый инвентарь) |
| item_neutral | int16 | Steam, если есть |
| net_worth | int32 | Steam |
| gold_per_min, xp_per_min | int16 | Steam |
| kills, deaths, assists | int8 | Steam |
| last_hits | int16 | Steam |
| avg_rank_tier | int8 / null | OpenDota /publicMatches (2.3) |

Оценка объёма: ~100 байт на игрока после сжатия, 1 млн матчей ≈ 1 ГБ сырья → **разбить по дням**, каждый файл ~50–100 МБ. Ассеты релиза GitHub до 2 ГБ каждый, в лимиты укладываемся. Если выйдет больше, хранить только нужные поля.

### 2.2. Фильтры матча
- Режимы: All Pick / Ranked All Pick (корзина normal), Turbo (корзина turbo). Остальные режимы отбрасываются.
- 10 игроков, нет покинувших игру (leaver_status > 1), длительность ≥ 15 мин (Turbo ≥ 10 мин).
- Патч: текущий крупный патч. Буквенные патчи (7.41a…f) не сбрасывают данные, но свежие матчи весят больше: **вес по давности**, половинный срок 21 день.

### 2.3. Ранги через OpenDota
`GET https://api.opendota.com/api/publicMatches` возвращает `match_id, match_seq_num, avg_rank_tier, num_rank_tier, lobby_type, game_mode` (проверено), по 100 матчей за запрос.
- Отдельный шаг сборщика: пройти publicMatches за тот же период (≤ 2500 запросов в день) и сохранить `match_id → avg_rank_tier` в `raw/ranks-YYYY-MM-DD.parquet`.
- Объединение по match_id на этапе расчёта. У матчей без ранга ставится null, в общей корзине они участвуют.
- Ранговые группы (крупные, чтобы данных хватало): **G1** Рекрут–Рыцарь (tier 1x–3x), **G2** Герой–Легенда (4x–5x), **G3** Властелин+ (6x–8x).
- Сначала проверь, какая доля наших матчей получает ранг. Если меньше 15%, ранги пока только как дополнительный слой (сглаживание к «всем рангам»).

## 3. Предобработка

1. **Дерево предметов** из dotaconstants (`items.json → components`). Для каждого предмета Y множество `up(Y)` = Y плюс все предметы, в которые он собирается (рекурсивно). Считаем «у H есть Y», если в итоговом инвентаре есть что-то из `up(Y)`.
2. **Кандидаты-ответы Y**: только завершённые предметы стоимостью ≥ 1000, которые покупаются в лавке. Расходники, варды, TP и нейтралки исключаются.
3. **Ключевые предметы врага X**: предметы, у которых слой механик нашёл признак (лечение, уклонение, BKB, невидимость, иллюзии, Linken и т.д.), плюс любой завершённый предмет ≥ 2000. Остальные не отслеживаются.
4. **Страты s** (сравниваем только похожие игры):
   - длительность: `<25`, `25–35`, `35–45`, `45+` мин (Turbo: `<15`, `15–22`, `22–30`, `30+`);
   - роль H в этой игре по месту в команде по нетворсу: **кор** (1–2), **тройка** (3), **саппорт** (4–5).

   Итого 12 страт. Роль-страта решает и вопрос «кор или саппорт»: совет для H считается в той роли, в которой H обычно играют (мода по данным), с возможностью переключить в настройках.

Для расчётов использовать **DuckDB** (SQL прямо по Parquet-файлам, без сервера): миллионы строк считаются за минуты на машине GitHub Actions.

## 4. Две метрики

Обозначения: игры героя H в страте s; «X есть» = у кого-то из врагов (или у E для уровня L1) в итоге есть предмет из `up(X)`.

### A. Адаптация (что игроки на H покупают, увидев X)
```
A_s = P(у H есть Y | X есть, s) − P(у H есть Y | X нет, s)
A   = Σ_s w_s · A_s,   w_s ∝ число игр H с X в страте s
```
Частоты сходятся быстро, это основной сигнал: коллективный опыт игроков на этом герое.

### B. Эффект (помогает ли Y именно против X): разность разностей
```
B_s = [WR(Y, X) − WR(¬Y, X)] − [WR(Y, ¬X) − WR(¬Y, ¬X)]     (всё внутри страты s)
B   = Σ_s w_s · B_s
```
Это и есть определение контр-предмета: насколько Y помогает сильнее, когда у врага есть X, чем когда его нет. Длительность и роль уже учтены стратами. Сигнал шумный, поэтому используется со сглаживанием и как фильтр и бонус, а не как главный критерий.

Ошибку обеих метрик считать по стратам (дисперсия разности долей), складывать с весами w_s².

## 5. Сглаживание по уровням (вместо порогов)

Контекст врага, от точного к общему:
- **L1**: у героя E есть X
- **L2**: у любого врага есть X
- **L3**: у любого врага есть предмет с той же механикой, что у X

Мой герой: **H** → запасной вариант **класс H** (основной атрибут × типичная роль: «ловкач-кор», «сила-тройка»…).

Оценка на уровне L1 стягивается к L2, L2 к L3:
```
θ_L1* = (n1·θ_L1 + k·θ_L2*) / (n1 + k)
```
k подбирается эмпирическим Байесом: k = (средняя дисперсия внутри ячеек) / (разброс истинных значений между ячейками), методом моментов по всем ячейкам уровня. Отдельно для A и для B. Стартовые значения, если оценка не выходит: k_A = 200, k_B = 800.

**Уверенность**: по числу игр `n` на самом точном уровне, чей вес в итоговой оценке ≥ 50% (то есть n1 ≥ k):
- высокая ≥ 1000, средняя 300–1000, низкая < 300.

При низкой уверенности процентов не показывать, только «мало данных» и совет по механике.

## 6. Итоговый выбор предмета

Для запроса (H, роль, ранг-группа, E, X):
1. **Кандидаты**: Y из п. 3.2, которые механически отвечают X или E (утверждённые правила) **или** входят в топ-5 по A. Второе ловит адаптации, которых нет в правилах. Такие помечаются «по опыту игроков».
2. **Оценка**: `S = A*/σ_A + λ·B*/σ_B`, λ = 1. Звёздочка — после сглаживания, σ — стандартное отклонение метрики по всем кандидатам.
3. **Вето**: если верхняя граница 90%-интервала B* < −2 п.п., предмет исключается (он вредит против X).
4. **Отсев в программе** (не в статистике): уже есть у меня (галочка → следующий); не по фазе игры (стоимость > бюджета по моему золоту и времени); герой H покупает Y реже 3% игр в этой роли.
5. **Два слота**: «сейчас» (лучший, что укладывается в ~3 минуты фарма) и «потом» (лучший вообще). Если это один и тот же предмет, показывается один.
6. **Несколько угроз**: если предмет попадает в топ-3 против двух угроз, он получает бонус +0.5 к S.
7. **Гистерезис**: совет меняется, только если новый S больше старого на 0.5.

Текст совета: `«{E} собрал {X} → на {H}: {Y} ({механика по-русски})»`. В полной карточке одна строка пояснения: «игроки на {H} берут его против {X} в {a:.1f} раза чаще, с ним выигрывают на {b:+.0f}% чаще ({n} игр)». Вторая половина только при высокой уверенности.

## 7. Что уходит в программу (готовые ответы, без расчётов на клиенте)

Сборщик после расчёта публикует `recs.zip`, разложенный по героям: программа читает только кусок своего героя. **Цель: память под советы ≤ 20 МБ, загрузка ≤ 1 с** (изменено автором 30.09 вместо «файл ≤ 5 МБ»: целый файл 8,5 МБ занимал в памяти +300 МБ; формат — `app/threats/recs_file.py`, DECISIONS №16–17):
- `item[bucket][rank_group][role][H][X]` → топ-6 `[Y, S, A*, B*, conf, n, flag_mechanic]`
- `item_hero[bucket][rank_group][role][H][E:X]` → топ-6, только связки с уверенностью не ниже средней
- `hero[bucket][rank_group][role][H][E]` → топ-6 против самого героя (для карточки в начале катки)
- `threat[bucket][rank_group][E]`: распределение ролей E по нетворсу, сила в лейте (WR 45+ минус WR <25 по стратам), матчапы H против E
- `meta`: патч, дата, число матчей по корзинам, доля матчей с рангом

Программа берёт `item_hero`, если там есть связка, иначе `item`, дальше делает отсев из п. 6.4–6.7. Старый `stats.json` удалить.

## 8. Проверка до интерфейса (обязательно)

1. **Вики-эталон** (вместо эталона автора, который отменён). `data/benchmark_counters.json`: для каждого героя список предметов из раздела «Bad against → Items» его страницы Counters на вики (собирает `tools/fetch_wiki_counters.py`). В проверке учитываются только предметы, которые могут быть ответом (кандидаты из 3.2); расходники, нейтралки и убранные из игры предметы пропускаются.
   **Критерий**: хотя бы один предмет из вики-списка героя E в топ-3 советов против E не меньше чем в 80% пар (герой, E).
2. **Проверка на отложенных днях.** Посчитать всё на днях 1…N−3 и проверить на последних 3 днях: у советов с высокой уверенностью знак B должен совпасть не меньше чем в 70% случаев.
3. **Отчёт автору (Markdown-таблица):** для 4 героев автора против Axe, Sniper, PA, Alchemist и против Heart, Butterfly, BKB, Blade Mail — топ-3 с A, B, n, уверенностью. Автор проверяет глазами. **Только после его «ок» переходить к интерфейсу.**

## 9. Порядок работы

1. **Сразу:** переделать сборщик на сырые данные (2.1–2.2) и сбор рангов (2.3). Старые суммы больше не копить. Чем раньше начнём сырой сбор, тем меньше потерь.
2. Скрипт расчёта на DuckDB (разделы 3–5) + тесты на маленьком искусственном наборе, где правильный ответ известен заранее (например, специально сделанная связка «Y помогает только против X»: B должен это найти, A не должен реагировать на длительность).
3. Когда наберётся ~1 млн матчей (при текущей скорости ≈ 10 дней), отчёт из раздела 8 → автор.
4. `recs.zip` + подключение в программе.
5. Интерфейс карточки и полоски (отдельная задача, после «ок» автора).

Каждый шаг заканчивается коротким отчётом автору: что сделано, цифры, что дальше. Никакой новой подгонки порогов «на глаз»: все константы в конфиге, у каждой комментарий, откуда она взялась.
