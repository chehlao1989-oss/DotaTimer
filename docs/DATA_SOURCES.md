**Прочитать перед любым изменением сборщика** (`tools/collect_raw.py`, `.github/workflows/stats.yml`) и перед любыми запросами к этим сервисам.
Сюда записывается каждый замер сразу, как он получен: дата, номер запуска, что меняли, что вышло.
Каждая цифра помечена: **замер** (откуда: номер запуска, файл, журнал) или **оценка**. Цифры в коде берутся только отсюда.

## Steam Web API: `IDOTA2Match_570/GetMatchHistoryBySequenceNum`

Что даёт: до 100 уже сыгранных публичных матчей за запрос (итоговые предметы, нетворс, режим). Ключ только в GitHub Secrets (`STEAM_API_KEY`).
Суточный лимит ключа 100 000 запросов (условия Steam Web API); мы делаем ~2 000 за запуск. Ошибка 429 суточный лимит не тратит, она стоит время ожидания.

### Замеры скорости
Цель — **максимум матчей в час**, а не минимум ошибок 429.

| №1, 29.09 09:08–10:38 UTC (старый сборщик сумм) | пауза 1,5 сек, после 429 ждать 60 сек | замер (журнал, пересказ): 429 на каждом 10–12-м запросе; остановлен вручную |

| №5, 29.09 18:42–20:34 UTC | то же, что №2 | замер (скриншот журнала, первые 500 запросов): при паузе 3 → 4,5 → 6 → 7,5 сек 429 на каждом ~22-м запросе; при 8,5–9 сек одна 429 за 400 запросов. Замер (файл `matches-2026-09-29-1841.parquet`): **64 725 матчей за 112 мин ≈ 34,7 тыс./час**. Шаг сбора кончился через 112 мин из 210 — см. «Ошибки» |

**Лучший результат на сейчас: запуск №5, ≈ 34,7 тыс. матчей/час** (замер).

### Текущая настройка (с 29.09 вечера, схема автора)
Регулятор: после 429 ждать `Retry-After` (если заголовка нет — 20 сек), пауза ×1,5; после 20 успешных подряд пауза ×0,9; пауза в пределах 1–10 сек; старт 3 сек.
После 20 ошибок подряд — ждать 5 мин и продолжать (не бросать сбор).
Журнал каждые 10 мин: запросов/мин, матчей/час, число 429, пауза.

**Решение по темпу — только по журналам:** ближайший запуск с регулятором сравнить с лучшим прошлым (матчей/час). Результат записать сюда. После этого настройку не трогаем.

### Сохранение и продолжение
- Каждые 15 мин собранное пишется частью `matches-<тег>-pNN.parquet` и сразу выкладывается в релиз `data-raw`. Падение или таймаут теряет не больше 15 мин.
- `next_seq.txt` в релизе (откуда продолжит следующий запуск) обновляется только после того, как все части до этого места выложены: следующий запуск продолжает с последнего **сохранённого** матча.
- Если `next_seq.txt` нет (первый запуск после старого сборщика) — старт по последнему матчу из последнего файла матчей в релизе.
- Итоги запуска — `run-<тег>.json` в релизе; отчёт в 5 строк: `python tools/report.py` (и в сводке запуска на GitHub).

### Сколько собирается
С 29.09 сбор постоянный: запуск каждые 6 часов (02:00, 08:00, 14:00, 20:00 МСК), до 290 мин на матчи + до 20 мин на ранги.
Оценка: при 34,7 тыс./час (замер №5) — ~165 тыс. матчей за запуск, ~650 тыс. в сутки. Проверить по первым запускам и записать факт.

## OpenDota API
- **Бесплатный лимит: 60 запросов в минуту и 3000 в сутки, считается по IP** (TZ.md 29.09; заголовок ответа `X-Rate-Limit-Remaining-Day`: 2704 из 3000 с компьютера автора 29.09 вечером — замер). У раннера GitHub каждый запуск свой IP.
- **Единственная логика лимита в сборщике рангов — заголовок ответа внутри запуска:** после первого запроса по остатку `X-Rate-Limit-Remaining-Day` считается, сколько запросов сделать (и шаг, чтобы раскидать их по всему диапазону номеров матчей запуска); при остатке 100 сбор останавливается; при 429 — тоже. Остаток пишется в журнал каждые 100 запросов и в итог. Кроме лимита шаг ограничен временем: 20 мин.
- В коде пауза 1,1 сек между запросами (60 в минуту).
- `/publicMatches?less_than_match_id=…` — ранги матчей (`avg_rank_tier`), 100 матчей за запрос.
- Замер №5 (старый шаг рангов, 17 мин): 69 700 матчей с рангом; у **52 495 из 64 725 наших матчей (81%)** есть ранг.
- `/matches/{id}` — отдаёт `match_seq_num`; для несуществующего номера 404.
- 29.09 днём при массовых запросах `/heroes/{id}/matchups` из программы получили 429 — такие запросы делать редко и с кешем.

### Ошибки, которые уже были (не повторять)
- 29.09 вечер: шаг рангов поставлен на 2 400 запросов за запуск без сверки с лимитом 3000/сутки из TZ.md. Потом поставили «700 на запуск» — тоже неверно, лимит по IP. Теперь только по заголовку ответа.

## GitHub Actions (где идёт сбор)
- Публичный репозиторий: минуты раннеров бесплатны. Одна задача — не дольше 6 часов (у нас таймаут 350 мин), до 20 задач одновременно на бесплатном плане (у нас одна).
- **Правила допустимого использования** (GitHub Terms for Additional Products and Features, раздел Actions) запрещают, в частности: майнинг; нагрузку на серверы, несоразмерную пользе для пользователей (примеры: CDN, serverless-приложения); на раннерах GitHub — «любую другую деятельность, не связанную с производством, тестированием, развёртыванием или публикацией программного проекта». GitHub может отслеживать использование.
- **Плановые запуски в публичном репозитории отключаются сами, если в репозитории 60 дней нет активности** (документация GitHub «Disabling and enabling a workflow»).
- **Риск (оценка):** сбор данных для своей программы можно считать частью проекта, но ~20 часов работы в сутки — заметная нагрузка, и формулировка «не связанная с проектом деятельность» оставляет GitHub право решать самому. Худший случай — отключение Actions в репозитории или предупреждение аккаунту.
- **Варианты (решает автор, пока не решено — ничего не меняем):**
  - А. Оставить 4 запуска в сутки (~20 ч): максимум данных, риск выше.
  - Б. 1–2 запуска в сутки (~5–10 ч): риск ниже, данных в 2–4 раза меньше.
  - В. Сборщик на своём компьютере (Планировщик заданий Windows) или на дешёвом сервере: правил GitHub это не касается; компьютер должен быть включён или сервер стоит денег.
  - Г. Смешанный: GitHub ночью + свой компьютер днём.
